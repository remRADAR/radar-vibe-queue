# RADAR SEO & Knowledge Engineering

> RECONSTRUCTED: Authored during the RADAR operating-skills expansion; the original expansion package was not available. Re-check current schema.org types and search-engine documentation at use time.

## Purpose and scope

Make RADAR properties and artists machine-understandable and discoverable: structured data (schema.org), artist identity consistency, canonical/authoritative references, metadata hygiene, and knowledge-graph eligibility. Out of scope: social growth tactics (radar-meta), generic content SEO copy edits (editorial).

## Triggers

Structured data audit, schema.org markup, artist identity disambiguation, canonical references, knowledge panel groundwork, rich-result eligibility, metadata consistency.

## Required inputs

Target page/property, current markup or CMS templates, artist identity facts (verified), and the intended authoritative source set.

## Procedure

1. Crawl or read the actual pages/templates; record what structured data exists today.
2. Validate existing markup (schema.org validator / Google Rich Results at use time); record errors and warnings as evidence.
3. Define the entity model: artist, musicRecording, MusicGroup, Organization for RADAR; use sameAs links to verifiable authoritative profiles only.
4. Specify the exact markup/template changes with expected rich-result eligibility; coordinate implementation with web-development.
5. After implementation, re-validate live output and record before/after evidence.

## Capability and permission checks

Live validation requires network access or the validator's current interface — verify before claiming results. No search engine guarantees: eligibility is not placement.

## Safety boundaries and approval gates

Never fabricate identity facts, sameAs links, or release data. Do not mark up unverified information. Schema claims must match page content. Never promise rankings.

## Verification

Validator output before/after, and the live-rendered markup matching the spec, are the evidence.

## Failure and escalation

Conflicting identity facts across platforms: mark UNKNOWN, request the authoritative answer, and document the decision in the ledger.

## Handoff and continuity

Record entity decisions and canonical sources in the project ledger so future agents do not re-litigate them.

## Completion criteria

Audit findings with evidence, an entity model, implemented-and-validated markup, or a documented blocker.
